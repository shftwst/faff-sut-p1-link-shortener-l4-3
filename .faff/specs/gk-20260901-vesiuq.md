This is the build spec for epic E2 of the link-shortener service (gitkey `gk-20260901-vesiuq`), written for the build agent and human reviewers. E2 extends the E1 skeleton (gitkey `gk-20260901-r99do5`, shipped and on main): it adds the first real golang-migrate migration, which creates the `links` table, and the persistence-layer methods that insert a link and fetch a link by code, wired into the existing `internal/store` package. E2 inherits E1's fixed stack (Go 1.22 stdlib `net/http`, Postgres 16, pgx v5, golang-migrate v4) unchanged; it decides no new architecture and stands up no new runnable surface. It stops short of the `POST /shorten` and `GET /{code}` HTTP endpoints (E3/E4) and of TTL expiry enforcement (E5).

## 1. WHY — problem and principles

The load-bearing idea: E1 shipped the migration *runner* against an empty `migrations/` directory, so the schema is still empty and the store package exposes no queries. E2 is the first slice that puts real data structure behind the running service: one migration file that creates the `links` table, and two store methods (insert, fetch-by-code) that read and write rows in it. After E2, the code→url mapping has somewhere to live, which is the precondition every later product endpoint depends on.

Problem statement: the running service has a datastore but no schema and no persistence code, so nothing can be stored or retrieved. E2 adds the `links` table via a versioned migration applied at startup and the store methods to insert and read a link. This resolves E1's deferred point that `schema_migrations` bookkeeping was not yet populated (E1 ran the runner against an empty dir on purpose).

Design principles:

- **Extend E1, do not re-architect it.** The stack, the migration runner (`internal/migrate`), the connection foundation (`internal/store` `Open`), and the DSN-scrubbing error discipline are fixed by E1. E2 adds a migration file and store methods inside those seams; it changes no existing interface and introduces no new dependency (golang-migrate and pgx are already in `go.mod`).
- **Idempotency comes from golang-migrate's version bookkeeping, not defensive DDL.** The migration is a plain `CREATE TABLE`, not `CREATE TABLE IF NOT EXISTS`. Applied-once-ness is guaranteed by the `schema_migrations` version row golang-migrate maintains; restart re-runs the runner, which finds nothing pending (`ErrNoChange`) and makes no change. Defensive `IF NOT EXISTS` would mask a genuine dirty-state or double-apply bug rather than expose it.
- **The store never leaks the DSN, matching E1.** E1 established that any error which could embed the connection string is scrubbed before logging. E2's query-path errors are wrapped and returned to the caller; they carry the failing SQL and Postgres error, never the DSN, so the query path needs no new scrubbing, but it must never wrap the DSN into an error either.
- **Persist the `expires_at` column now; enforce nothing on it.** The `expires_at` column is part of E2's schema because the table shape is decided here, but TTL semantics (computing it from `ttl_seconds`, expiry-on-read, expired-code 404) are epic E5. E2 stores whatever `expires_at` a caller supplies (in practice `NULL` until E5) and reads it back unchanged; it applies no expiry logic.

## 2. OUT OF SCOPE

- **`POST /shorten` mint endpoint** — validating a URL, minting a 7-char base62 code, calling `Insert`. Why excluded: epic E3. Extension point: a new handler on `internal/httpapi`'s router that constructs a `Link` and calls `Links.Insert`.
- **`GET /{code}` redirect and 404** — resolving a code to a URL, issuing a 302, mapping the not-found sentinel to 404. Why excluded: epic E4. Extension point: a wildcard `GET /{code}` handler that calls `Links.ByCode` and maps `ErrLinkNotFound` to a 404.
- **TTL expiry semantics** — deriving `expires_at` from a `ttl_seconds` input, treating an expired row as absent, returning 404 for an expired code. Why excluded: epic E5. Extension point: E5 computes `expires_at` at mint time and adds an expiry predicate to the read path (`ByCode`, or a new method); E2 only stores and returns the column.
- **Code generation / uniqueness policy** — deciding how a code is minted or how collisions are retried. Why excluded: epic E3 owns minting. E2's `Insert` surfaces a duplicate-key condition as a typed error so E3 can retry, but it neither generates codes nor decides the retry policy. Extension point: E3's mint loop consumes `ErrDuplicateCode`.
- **Wiring the repository into an HTTP handler or `main.go`** — constructing `Links` in `main` and passing it to the router. Why excluded: no endpoint consumes it until E3, so wiring it now would be dead code. The repository is exercised by its own integration test against the composed Postgres. Extension point: E3 constructs `NewLinks(pool)` and hands it to the router alongside the existing pool.
- **Secondary indexes on `links`** — e.g. an index on `expires_at` for an expiry sweep. Why excluded: no E2 query filters on `expires_at`; the primary-key lookup on `code` needs no extra index. Extension point: a later migration under `migrations/` if E5/E6 add an expiry query.

## 3. WHAT — vocabulary, types, and interfaces

Vocabulary:

| Term | Definition |
|---|---|
| link | A stored mapping from a short `code` to a destination `url`, with a creation timestamp and an optional expiry timestamp. |
| code | The short identifier that is the primary key of the `links` table. Stored as text; E2 presumes no particular length or alphabet (E3 mints it). |
| repository | The `Links` type in `internal/store` that owns the SQL for inserting and fetching a link. |
| `schema_migrations` | The bookkeeping table golang-migrate maintains to record the applied migration version and whether the last migration left the schema dirty. |

### Schema — the `links` table

The migration creates exactly this table. Column types are Postgres types.

```
TABLE links:
  code        TEXT         PRIMARY KEY          # the short code; natural key, lookups are by code
  url         TEXT         NOT NULL             # destination URL, stored verbatim; no length cap
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()   # row creation time, DB-assigned
  expires_at  TIMESTAMPTZ  NULL                 # optional expiry; NULL means no expiry. E2 stores, E5 enforces.
```

- No surrogate key: `code` is the primary key, so a duplicate code insert fails with a unique-violation the store maps to `ErrDuplicateCode`.
- No `CHECK`, no foreign keys, no secondary indexes in E2.

### Migration files

Two files under `migrations/`, a golang-migrate versioned pair (6-digit sequential prefix, the golang-migrate default the E1 runner already reads via the file source):

```
migrations/000001_create_links.up.sql     # CREATE TABLE links ( ... )   -- plain CREATE, not IF NOT EXISTS
migrations/000001_create_links.down.sql   # DROP TABLE IF EXISTS links
```

The `up` file creates the table exactly as the schema above. The `down` file drops it. E2 never runs `down` automatically; the pair exists because golang-migrate expects both directions and a reviewer needs the reverse to be correct.

### Types — the store surface (added to `internal/store`)

```
RECORD Link:
  Code:       string        # maps to links.code (NOT NULL PK). E2 persists whatever non-null string it is given.
  URL:        string        # maps to links.url (NOT NULL). E2 persists whatever non-null string it is given.
  CreatedAt:  Timestamp     # maps to links.created_at; DB-assigned on insert, populated on read
  ExpiresAt:  Timestamp?    # maps to links.expires_at; nil ⇔ SQL NULL

REPOSITORY Links:
  # Constructed from the E1 pgxpool. Holds the pool; owns the links SQL.
  NewLinks(pool: *pgxpool.Pool) -> *Links

  # Insert persists one link row. code is the primary key.
  #   - On success: returns nil. created_at is DB-assigned (DEFAULT now()).
  #   - On a duplicate code (unique_violation, SQLSTATE 23505): returns ErrDuplicateCode.
  #   - On any other DB error: returns a wrapped, DSN-free error.
  Insert(ctx: Context, link: Link) -> error

  # ByCode fetches one link by its code.
  #   - On a hit: returns the fully-populated Link, nil.
  #   - On no row: returns zero Link, ErrLinkNotFound.
  #   - On any other DB error: returns zero Link, a wrapped DSN-free error.
  ByCode(ctx: Context, code: string) -> (Link, error)

SENTINELS:
  ErrLinkNotFound    # ByCode found no row; E4 maps this to a 404
  ErrDuplicateCode   # Insert hit a duplicate primary key; E3 maps this to a mint retry
```

**Insert and `created_at` / `expires_at`.** `Insert` writes `code`, `url`, and `expires_at` and lets the DB default supply `created_at`. It does not read `link.CreatedAt` on the way in. `expires_at` is bound as `NULL` when `link.ExpiresAt` is nil and as the timestamp otherwise.

**Validation ownership — E2 persists, it does not validate.** E2's store methods enforce only what the schema enforces: `NOT NULL` on `code` and `url`, and PK uniqueness on `code`. E2 does **not** reject an empty-string code or url, does not validate that `url` is a well-formed absolute URL, and does not constrain the code's length or alphabet — the DB `TEXT` columns accept any non-null string, of any length, in any UTF-8 content. Rejecting an empty or malformed URL and minting a well-formed 7-char base62 code are **E3's** responsibilities (`POST /shorten`); enforcing them in E2 would pull E3's input-validation forward and duplicate it. The `links` table therefore stores exactly what it is handed, and the round-trip scenarios below prove it does so losslessly for varied and long inputs.

**Design decision — repository shape vs package funcs.** Options: (a) a `Links` struct holding the pool with methods; (b) package-level functions taking a `*pgxpool.Pool` on each call. E1's own OUT OF SCOPE names "a `Links` repository in `internal/store`", and a struct gives E3/E4 a single value to hold and pass to handlers. **Chosen:** a `Links` repository struct constructed by `NewLinks(pool)`. Package funcs would force every future handler to thread the pool through each call.

**Design decision — `code` column type.** Options: `TEXT`, or `CHAR(7)` / `VARCHAR(7)` to match the eventual 7-char code. **Chosen:** `TEXT PRIMARY KEY`. E3 owns the 7-char base62 rule; baking length into the schema here would couple E2 to an E3 decision and force a migration if E3's format ever changed. `TEXT` in Postgres has no performance penalty over `VARCHAR` and accepts any length and any UTF-8 content, so E2 presumes no code alphabet or length — a longer or non-ASCII code round-trips losslessly (proven by a scenario below).

## 4. HOW — behaviour

**Architecture and approach.** E2 touches two seams, both already built by E1:

1. **Migration.** Dropping the `000001_create_links.{up,down}.sql` pair into `migrations/` is the entire startup-side change. `cmd/api/main.go` already calls `migrate.Run(cfg.DatabaseURL, "migrations")` at boot; `internal/migrate` already applies pending `.sql` files via golang-migrate's file source and treats `ErrNoChange` as success. With one real file present, the empty-dir short-circuit in `migrate.Run` no longer fires (the dir now contains a `.sql` file), so the runner calls `m.Up()`, which applies version 1 and writes the `schema_migrations` row. No Go code in `main.go` or `internal/migrate` changes.

2. **Store methods.** `internal/store` gains the `Link` record, the `Links` repository, `NewLinks`, `Insert`, `ByCode`, and the two sentinels, using the same pgx v5 pool E1's `Open` already returns. `store.go`'s existing `Open`/`SafeReason` are unchanged.

**Insert behaviour.**

```
PROCEDURE Insert(ctx, link):
  1. Execute:
       INSERT INTO links (code, url, expires_at) VALUES ($1, $2, $3)
     binding $3 = NULL when link.ExpiresAt is nil, else the timestamp.
     (created_at is omitted so the column DEFAULT now() supplies it.)
  2. IF the DB reports unique_violation (SQLSTATE 23505):
       return ErrDuplicateCode
  3. IF any other DB error:
       return a wrapped error whose text carries the DB error, never the DSN
  4. ELSE return nil
```

**ByCode behaviour.**

```
PROCEDURE ByCode(ctx, code):
  1. Execute:
       SELECT code, url, created_at, expires_at FROM links WHERE code = $1
  2. IF no row (pgx.ErrNoRows):
       return zero Link, ErrLinkNotFound
  3. IF any other DB error:
       return zero Link, a wrapped DSN-free error
  4. ELSE scan into Link (expires_at → nil when SQL NULL) and return it, nil
```

**Migration applied-once / restart idempotency.**

```
PROCEDURE startup_migration (unchanged E1 runner, new file present):
  1. migrate.Run sees migrations/ is non-empty (a .sql file exists) → skips the empty-dir short-circuit
  2. Constructs the golang-migrate runner and calls m.Up()
  3. First boot: version 1 pending → CREATE TABLE links runs; schema_migrations = (version 1, dirty false); status "applied"
  4. Later boot: version 1 already applied → m.Up() returns ErrNoChange → status "no change"; no DDL runs, table unchanged
```

Idempotency on restart is therefore a property of golang-migrate's `schema_migrations` version row, not of the DDL. The `CREATE TABLE` is plain (no `IF NOT EXISTS`): if it ever ran twice against the same schema it would error loudly rather than silently succeed, which is the behaviour that would surface a bookkeeping bug.

**Edge cases and error handling.**

- **Duplicate code on insert** → `ErrDuplicateCode` (mapped from SQLSTATE 23505). Terminal for E2; E3 decides whether to retry with a fresh code. `Insert` distinguishes it from other errors so the caller need not parse pgx error text.
- **Unknown code on fetch** → `ErrLinkNotFound`. Terminal, expected, not an error condition to log at error level. E4 maps it to 404.
- **`expires_at` round-trip** → a `NULL` `expires_at` reads back as a nil `ExpiresAt`; a non-nil timestamp reads back equal (to the DB's timestamptz precision). E2 applies no comparison against `now()`.
- **DB unreachable mid-query** → the pgx call returns a connection error; `Insert`/`ByCode` wrap and return it. It reaches the caller, not the logs directly, and carries no DSN (the DSN lives only in the pool config, not in query-path errors).

**Failure modes.**

- **The failure:** the migration lands the runner in a *dirty* state (a `CREATE TABLE` that partially fails, or a crash mid-apply), after which golang-migrate refuses further migrations until the version is forced clean. **How you'd know:** `SELECT dirty FROM schema_migrations` returns `true`, and the api boot logs `migrate_failed` and the container crash-loops (the port never binds). **What it means:** for a single `CREATE TABLE` this is unlikely, but if seen, the fix is operational (force the version), not a spec change; the born-verifiable check below asserts `dirty = false` so this does not pass silently.
- **The failure:** the store methods "work" in a unit test with a mock but the real column types or NULL handling differ (e.g. `expires_at` NULL scanned into a non-pointer). **How you'd know:** the integration test against the composed Postgres fails on the NULL round-trip or the type scan, not the mock. **What it means:** E2's verification must run against a real Postgres (the composed db or an equivalent), never only a mock — see Scenarios.

**Anti-pattern:** `CREATE TABLE IF NOT EXISTS links`. Why: it makes a double-apply silently succeed, hiding the exact `schema_migrations` bookkeeping bug the plain `CREATE TABLE` plus version tracking is there to catch.

**Anti-pattern:** returning the raw pgx error from `Insert` on a duplicate. Why: it forces every caller (E3) to string-match pgx internals; the typed `ErrDuplicateCode` is the store's contract.

**Anti-pattern:** enforcing or interpreting `expires_at` in E2 (comparing it to `now()`, skipping expired rows). Why: that is E5's TTL slice; doing it here silently pulls E5 forward and breaks the slice boundary.

## 6. Design decision rationale

**How is the `links` table versioned and applied?**
- Options: a golang-migrate numbered pair applied by the existing E1 runner; a hand-run SQL script; an ORM auto-migrate.
- The E1 runner already reads `file://migrations` and applies pending `.sql` files at boot; a hand-run script or ORM would duplicate or bypass it.
- **Chosen:** a `000001_create_links.{up,down}.sql` golang-migrate pair applied by the unchanged E1 runner. This is the seam E1 built for exactly this.

**Where does restart idempotency come from?**
- Options: rely on golang-migrate's `schema_migrations` version bookkeeping with a plain `CREATE TABLE`; use `CREATE TABLE IF NOT EXISTS` as a belt-and-braces guard.
- `IF NOT EXISTS` would mask a double-apply or dirty-state bug; the version row is the real guarantee and is independently checkable.
- **Chosen:** plain `CREATE TABLE`, idempotency via `schema_migrations`. Restart re-runs the runner, which returns `ErrNoChange`.

**What shape is the persistence API?**
- Options: a `Links` repository struct with methods; package-level functions taking a pool.
- E1's OUT OF SCOPE already names a `Links` repository; a struct gives E3/E4 one value to hold.
- **Chosen:** a `Links` struct via `NewLinks(pool)` with `Insert` and `ByCode`.

**What type is `code`?**
- Options: `TEXT`, `CHAR(7)`, `VARCHAR(7)`.
- Fixing a length couples E2 to E3's minting format.
- **Chosen:** `TEXT PRIMARY KEY`.

**How is a duplicate code surfaced?**
- Options: a typed `ErrDuplicateCode` sentinel mapped from SQLSTATE 23505; return the raw pgx error and let the caller parse it.
- The caller (E3) needs to tell a collision from a real failure without string-matching pgx internals.
- **Chosen:** map SQLSTATE 23505 to `ErrDuplicateCode`. The mapping is a property of a correct insert method, not E3's retry policy (which stays in E3).

## 8. DONE — definition of done

### From WHY
- [ ] The running service can store and retrieve a code→url mapping: after `docker compose up`, a link inserted through the store layer is readable by code.
- [ ] `schema_migrations` bookkeeping is populated (E1's deferred point): version 1 is recorded after first boot.

### From WHAT (schema)
- [ ] A `links` table exists with columns `code TEXT PRIMARY KEY`, `url TEXT NOT NULL`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `expires_at TIMESTAMPTZ NULL`.
- [ ] The migration is the versioned pair `migrations/000001_create_links.up.sql` and `migrations/000001_create_links.down.sql`; the up file is a plain `CREATE TABLE` (no `IF NOT EXISTS`), the down file drops the table.
- [ ] The down migration is functionally correct, not just present: applying it removes the `links` table (verified by a migrate-down test / golang-migrate `Down`), and re-applying up restores the table.
- [ ] The up migration uses a plain `CREATE TABLE` (no `IF NOT EXISTS`): executing the raw up DDL a second time against a DB that already has the table errors with "relation already exists".

### From WHAT (store surface)
- [ ] `internal/store` exposes a `Link` record with fields `Code string`, `URL string`, `CreatedAt` timestamp, `ExpiresAt` nullable timestamp (nil ⇔ SQL NULL).
- [ ] `internal/store` exposes `NewLinks(pool) *Links`, `Insert(ctx, Link) error`, `ByCode(ctx, code) (Link, error)`, and the sentinels `ErrLinkNotFound` and `ErrDuplicateCode`.
- [ ] E1's existing `Open` and `SafeReason` are unchanged.

### From HOW (behaviour)
- [ ] `Insert` persists `code`, `url`, `expires_at` and lets the DB DEFAULT supply `created_at`; a nil `ExpiresAt` binds SQL NULL.
- [ ] `Insert` returns `ErrDuplicateCode` on a duplicate primary key (SQLSTATE 23505) and a DSN-free wrapped error otherwise.
- [ ] `ByCode` returns the populated `Link` on a hit, `ErrLinkNotFound` on no row, and a DSN-free wrapped error otherwise; a NULL `expires_at` reads back as nil.
- [ ] A non-nil `expires_at` round-trips through Insert→ByCode equal to the DB's timestamptz precision (microseconds), with no timezone shift and no truncation.
- [ ] `created_at` is DB-assigned: inserting a Link whose `CreatedAt` is the zero value yields a fetched `CreatedAt` that is non-zero and within the `[just-before-insert, just-after-fetch]` window — proving the value came from `DEFAULT now()` and not the caller (since `Insert` omits `created_at` from the INSERT column list, an app-set value could not appear).
- [ ] No query-path error returned by the store contains the DSN — verified by forcing a real query failure and asserting the returned error text carries neither the DSN nor the password in plain, percent-encoded, or path-escaped form.

### From HOW (idempotency)
